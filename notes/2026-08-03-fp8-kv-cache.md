# FP8 KV cache：**过了 B1-R，省 ~12.3 GiB**（今天第一个正面结论）

日期：2026-08-03 · 模型：`unsloth/Qwen3.6-27B-NVFP4`（标准模型）·
分支 `work/fp8-kv-20260803` @ `e2c9ebe` · 单卡 RTX PRO 6000 Blackwell Max-Q

## 结论

**可用。** 每条判据都有 2–8× 余量，显存省约 12.3 GiB。
**当前默认关**（`QSR_QWEN36_FP8_KV=1` 开启），建议在后续提交里翻成默认开。

## 它为什么一直没做——一条错误的前提

`runtime/model/qwen36_model.py` 的模块 docstring 曾写着：本 checkpoint 声明
`kv_cache_quant_algo: FP8` 但**发货零个 `k_scale`/`v_scale`**（B0-2），
所以"该用什么 scale"无解，用 BF16 KV 绕开。

**那个观察测的是 `nvidia/`。** 标准模型实测：

| checkpoint | k_scale | v_scale |
|---|---:|---:|
| `nvidia/`（B0-2 当时看的） | 0 | 0 |
| `unsloth/`（**标准模型**） | **16** | **16** |

32 个 bf16 标量，**每层真的不同**（0.023–0.27），加上完整的 `kv_cache_scheme`
（`num_bits=8`、`strategy=tensor`、`symmetric=True`、`observer=static_minmax`）。
一直没人消费——`load_qwen36_model` 不像 Laguna 路径那样调
`apply_kv_cache_scale_post_load`。

**是新加的反向 loader 检查在第一次真实运行时把它报出来的**
（`warn_on_unconsumed_tensor_families`，见
[`2026-08-03-production-memory-audit.md`](2026-08-03-production-memory-audit.md)）。

**历史也印证**：`/home/bot/project/qsr-hist`（`8f5c195`）里
`runtime/direct_model_runner.py:1192` 是 `kv_cache_dtype: str = "fp8_e4m3"`
——**FP8 KV 当年是这个模型的默认值、在生产里跑过**，不是没验证过的新路子。

## 判据（`scripts/verify_fp8_kv_full_model_gap.py`，3 负载 × 65 步）

| 指标 | 实测 | 判据 | 余量 |
|---|---:|---:|---:|
| `median_gap_error` | **0.125** | 0.25 | 2× |
| `p90_gap_error` | **0.25** | 0.5 | 2× |
| `p90_logprob_error` | **0.312** | 0.5 | 1.6× |
| 最差负载 `mean_kl_topk` | **6.2e-4** | 5e-3 | 8× |
| `disagreement_rate` | **0.0051** | 0.03 | 5.9× |

**没有任何负载溢出 top-1024 捕获窗口**——这正是 W4A4 与 FP8 W8A8 双双栽掉的地方
（[`w4a4`](2026-08-03-w4a4-blockscaled-negative-result.md) /
[`w8a8`](2026-08-03-fp8-w8a8-preflight-negative.md)）。**对比很说明问题：
量化 KV 没事，量化激活不行。**

## 显存

capacity=1、num_slots=2，外部 `nvidia-smi`，真实服务进程：

| | MiB |
|---|---:|
| BF16 KV | 60,321 |
| **FP8 KV** | **47,689** |
| **省** | **~12.3 GiB** |

KV 那一行精确减半：**8192 → 4096 MiB/槽**。
并且用两个真实 `/v1/completions` 请求端到端验过（CUDA Graph 成功捕获、输出连贯正确），
**不是只看分配数字**。

⚠️ 基线 60,321 MiB 与
[`2026-08-03-production-memory-audit.md`](2026-08-03-production-memory-audit.md)
的 72.39 GiB 不是同一次测量（那次在释放 FP8 原件之前，且 harness 配置不同）。
**两者不可直接相减**；本表内部自洽。

## 途中修掉两个会静默出错的 bug

两个都会在 flag 打开后带着错误行为上线：

1. **Q 被一起量化成 FP8。** `q_for_kernel = query.to(cache.k_cache.dtype)` 这类转换
   在 KV 变 FP8 后会把 **query 也降成 FP8**——而 sparkinfer 的契约是
   "FP8 KV needs **BF16 queries** + k/v descales"。两处调用点
   （`Qwen36Attention.forward`/`decode_batch`，以及 `warmup_attention_shapes`），
   各自被一次真实 GPU 崩溃抓到。
2. **`index_copy_` 不支持 `float8_e4m3fn`**（本 CUDA 构建），批量 decode 的写入路径会炸。
   改成普通索引赋值——与单序列路径本来就在用的同一个操作。

scale 用法：`(key / k_scale).to(fp8)`，与 Laguna 既有 FP8 KV 路径同一约定
（`k_cache[...] = (key / layer._k_scale).to(torch.float8_e4m3fn)`）。

## 与前缀缓存的交互：不存在碰撞

历史代码把 `kv_cache_dtype` 编进每个 block 的链式 hash `extra_keys`，
理由是"fp8 与 nvfp4 的 KV 绝不能在同一 token 前缀上撞车（R7）"
（`qsr-hist` 的 `direct_model_runner.py:1437-1439`、`:4359`）。

**今天不成立**，独立核实过：`Qwen36Backend.reconcile_prefix_hit` 按**同 slot 线性
token 比对**匹配，**从不跨 slot 共享 KV 字节**，且 `kv_cache_dtype` 在进程生命周期内固定
——那个碰撞场景在结构上不可达。

## 建议

**翻成默认开。** 每条判据 2× 以上余量、是目前找到的最大一笔显存杠杆、且与历史默认一致。
